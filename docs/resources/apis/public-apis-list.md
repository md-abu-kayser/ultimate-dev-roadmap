# Public APIs List

> **Purpose:** curated learning and reference guidance.

## How to use this resource list

Use a primary source for correctness and a secondary source for explanation. Do not turn resource collection into procrastination. Pick one resource, build something, and return only when a gap appears.

## Selection criteria

- Relevance to the current learning goal
- Quality of explanations and examples
- Evidence of maintenance or stable foundational value
- Clear licensing / usage expectations
- Practical exercises or reference value

## Professional habit

Record **what you used, what you learned, and what you built**. The goal is skill acquisition, not bookmark accumulation.

## Evaluation workflow

When you pick a resource, record:

1. **Authority:** is it primary documentation, a reputable textbook, or a community explanation?
2. **Freshness:** could the information have changed with a new release?
3. **Depth:** does it explain why, or only show steps?
4. **Practice:** can you turn it into a small build?
5. **Transfer:** can you explain the idea without the original resource?

This prevents resource collecting from replacing practice.

## Professional Review Standard

### Purpose
Use this page as a curated learning index. Treat API providers as dependencies with contracts, quotas, authentication, failure modes, and lifecycle concerns.

### How to use this page

1. Choose one resource or item that matches your current learning objective.
2. State what you expect to learn before opening it.
3. Verify important claims against primary documentation when possible.
4. Produce an artifact: code, notes, benchmark, diagram, test, or decision record.
5. Record what was useful, what was outdated, and what you would recommend to another engineer.

### Selection criteria

| Criterion | Ask |
|---|---|
| Authority | Who maintains or publishes it? |
| Recency | Is the material appropriate for the technology version or era you are using? |
| Depth | Does it explain mechanisms and trade-offs, not just commands? |
| Practice | Can you turn the material into an experiment or project? |
| Reliability | Can important claims be cross-checked? |

### Learning output

Do not finish a resource with “I watched/read it.” Finish with evidence:

```text
Resource → Concept → Experiment → Result → Lesson → Next action
```

### Anti-patterns

- Bookmark hoarding without practice.
- Treating a third-party tutorial as normative documentation.
- Copying configuration without understanding why it exists.
- Using an old example unchanged in a newer environment.

### Readiness gate

- [ ] I can explain why I selected the resource.
- [ ] I verified the most important claims.
- [ ] I created a practical artifact from it.
- [ ] I documented one limitation or caveat.
- [ ] I can recommend or reject it with reasons.
